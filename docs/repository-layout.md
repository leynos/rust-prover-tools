# Repository layout

This document is the canonical description of the repository's shape: where
source, tests, fixtures, plans, and reference material live, and which path
owns which boundary. The tree below is a compact orientation sketch, not an
exhaustive listing; every directory named here is real, and `__pycache__`
directories are omitted.

```text
.
├── AGENTS.md                 Assistant and contributor rules for this repository
├── Makefile                  Every gate: fmt, check-fmt, lint, typecheck, test,
│                             spelling, markdownlint, nixie, and the aggregated `all`
├── README.md                 Project overview and the entry-point document index
├── pyproject.toml            Packaging, ruff/pylint/ty configuration, pytest settings
├── typos.toml                Generated spelling configuration; never edited by hand
├── typos.local.toml          Narrow repository-specific spelling exceptions
├── docs/                     Hand-written reference, design, and plan documents
│   └── execplans/            Living execution plans, one per work stream
├── rust_prover_tools/        The package: prover tooling, CLI, and supervision
├── scripts/                  Vendored shared-actions tooling
└── tests/                    Behavioural tests, fixtures, and BDD features
```

## Top-level files

- `AGENTS.md` holds the working rules: code style, testing procedure, gate
  expectations, and Markdown conventions. Read it before changing code.
- `Makefile` is the only supported way to run a gate. `make all` chains
  `build`, `check-fmt`, `lint`, `typecheck`, `test`, `spelling`,
  `test-workflow-contracts`, and `actionlint`; run it before every commit.
- `pyproject.toml` owns packaging and tool configuration, including the
  400-line module limit that pylint enforces and the ruff rule selection.
- `typos.toml` is generated by the pinned `typos-config-builder`; put
  exceptions in `typos.local.toml` and commit the regenerated file.

## `docs/`

Long-lived reference material. The documents most relevant to changes in this
package are:

- `users-guide.md` for every command and option.
- `developers-guide.md` for how to work on the project: gates, corpus rules,
  module responsibilities, and the prover CLI internals.
- `kani-supervised-execution.md` for the design and reference of the
  supervision capability.
- `prover-tools-cli-design.md` for the command architecture.
- `documentation-style-guide.md` for the house documentation rules.
- `roadmap.md` for planned work, and `execplans/` for the living plan behind
  each work stream.

## `rust_prover_tools/`

The package root holds the CLI, the command layer, installation and release
handling, and the public API in `__init__.py`. Four subpackages carry the
prover-specific work:

- `kani_log/` is the shared Kani 0.67.0 grammar, report model, reader, and
  reconciliation, with its provenance in `ATTRIBUTION.md`.
- `kani_inventory/` resolves Cargo packages and targets, scans Rust sources
  lexically, follows modules and `#[path]`, and serializes the strict version-1
  inventory document.
- `kani_snapshot/` pins, installs, verifies, and publishes Kani releases.
- `supervision/` is the prover-neutral supervisor: process groups, live
  evidence, resource sampling, limits, typed outcomes, and reporting. The Kani
  adapter lives inside it as `kani.py` and `kani_outcome.py`, because the
  adapter seam is small and prover-neutral.

## Module responsibilities

These modules carry a boundary that a contributor has to know before editing
them. The remaining module-by-module responsibilities of `supervision/` and the
Kani adapter are documented in `developers-guide.md` under "Kani supervised
harness execution".

- `rust_prover_tools.kani_cli_grammar` is the single registry of Kani release
  grammars. `KANI_067` is the qualified 0.67.0 entry, `grammar_for` resolves a
  release, `SUPPORTED_VERSIONS` lists the registered set, and
  `UnsupportedKaniGrammarError` refuses an unregistered one. An import-time
  check ties the registry to `SUPPORTED_KANI_VERSIONS` from `kani_log`, so a
  release cannot be half-registered.
- `rust_prover_tools.supervision.launcher` owns the launch boundary:
  `CuprumHarnessLauncher` starts one child in an owned process group through
  Cuprum and returns a `RunningHarness`. Cuprum types stop at the launcher,
  `pipe_drain` and `launch_pid`; every other supervision module is
  prover-neutral and Cuprum-free.
- `rust_prover_tools.supervision.pipe_drain` borrows the child's pipe ends
  through `StdioTarget.fd`, forwards decoded lines, and translates the neutral
  `LaunchEnvironment` back to Cuprum's environment mode at that boundary.
- `rust_prover_tools.supervision.stream_lines` is the bounded splitter the pipe
  drain uses, so an unterminated child line is capped in one place. The Kani
  parser has its own bounded line window in `kani_log.lines`, because it must
  retain a few lines for description lookahead.
- `rust_prover_tools.supervision.cgroup` reads cgroup v2 membership and memory
  evidence from procfs and the mount table, returning explained absences rather
  than zeroes when the hierarchy is unavailable.

## `tests/`

Behavioural tests and the fixtures they read. The package's own unit tests live
in `rust_prover_tools/unittests/`, next to the modules they exercise.

- `fixtures/kani_logs/<version>/` holds the captured Kani transcripts that
  qualify the parser. These are evidence: recapture them, never hand-edit them.
- `fixtures/kani_harness_workspace/` is a small Cargo workspace whose proofs
  exercise discovery, selection, and attribution.
- `fixtures/verus_logs/<release>/` is the equivalent corpus for Verus.
- `features/` holds the BDD feature files used by the behavioural suite.

Anything under `tests/fixtures/` is reference data. Changing it changes what
the gates prove, so treat a fixture edit as a test change.
